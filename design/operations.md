# Operations

Desired operational contracts for one isolated mailbox agent. These are target requirements; items labeled **Target** may not be implemented yet. Current delivery state and evidence live in the [roadmap](../docs/roadmap/ROADMAP.md) and [implementation record](../docs/implementation.md).

## Deployment and observability

The primary deployment is a non-root Linux container with a read-only application filesystem and a persistent, private local state volume. The CLI remains supported for local development and controlled operations. Each process or container serves one mailbox and owns its configuration, credentials, connections, and state. Run one active owner per mailbox/state root. SQLite state requires local filesystem locking; do not share it over a network filesystem.

Polling is the default intake and requires no public inbound endpoint. **Target:** local structured health and status report process readiness, mailbox synchronization, dependency errors, queue/run state, pending approvals, retention, and unresolved external effects. They expose safe metadata only and never require a public HTTP endpoint. Public health endpoints, notifications, webhooks, and backfill are optional extensions with explicit authentication, authorization, and deployment contracts.

The first synchronization baseline is visible as a distinct state. Existing messages remain unprocessed unless an explicitly configured backfill feature is introduced. Checkpoint advancement and accepted work must be atomic. Cursor or permission failures stop intake visibly; the service must not silently reset its cursor or imply that history was recovered.

## Reliability and external effects

Persist accepted work, exact approvals, action fences, and pending delivery state before external effects. Use bounded time, model, tool, queue, response-size, and context budgets. Retries for safe reads use bounded exponential backoff with jitter, honor provider `Retry-After`, and remain within the original work/deadline budget. Do not retry mutations merely because a response was lost.

The initial retry policy covers Graph metadata/message GETs and client-credentials token acquisition, with at most three attempts inside one configured mailbox timeout and the caller's remaining budget. It does not replay inference, MCP calls or sends. A provider wait beyond that deadline defers Graph-dependent work for the mailbox connection; persist its earliest permitted retry time across restart rather than retrying before the provider window. Local/model/MCP work that needs no Graph access may continue. Throttled metadata is deferred, not classified as an unsupported document; queued work and pending sends preserve their state and budgets. Uncertain mutations remain fenced.

Every external mutation has an uncertainty boundary. A write whose outcome is unknown remains fenced from automatic replay until reconciled against authoritative provider or adapter evidence. A provider's accepted response is not proof of recipient delivery. Operator resolution records actor, target, evidence/reason, and outcome. Exactly-once delivery is not promised.

On restart, resume durable work without granting new execution budget or replaying uncertain effects. Preserve FIFO behavior where ordering is part of the mailbox contract. Cancellation and dependency outage must leave a visible, recoverable state. Recovery instructions identify which actions are safe to repeat and which require evidence first.

Retain raw messages, context, replies, tool arguments/results, and instruction snapshots only for the configured content period. Keep audit metadata for its configured period. Retain content-free replay identities and action/send fences indefinitely, including unresolved outcomes, to prevent replay after content expiry. Filter/paginate operational queries and monitor metadata growth. Backups and filesystem snapshots have independent retention and access controls.

Status/health use transition-maintained counts and indexed, capped metadata queries rather than loading all retained run/action JSON. Pages use immutable admission sequence and run identity rather than a clock or last-update timestamp. Recovery, queue selection and retention also select bounded work explicitly. Pending approvals count toward queue capacity. Introducing those projections requires an atomic, versioned migration and a forward-version guard; a one-time migration scan must be declared separately from normal operational queries.

## Backup, recovery, and change management

Back up the persistent state consistently while the process is stopped or using a supported consistent-snapshot procedure. Protect secrets separately. A restore must preserve deduplication identities, approvals, checkpoints, and unresolved fences. Before resuming a restored state, reconcile the entire interval after the snapshot against provider/adapter evidence: both snapshot-era work and later inbound messages missing from the restored deduplication ledger can have completed external effects. A consistent backup does not establish whether those effects occurred.

**Target:** stopped backup takes the same exclusive owner lease without migrating or recovering the source. Export a standalone database plus a small identity/version/time/checksum manifest into a private, non-overwriting snapshot directory. Validate integrity and retain configuration/instruction versions and secrets separately. Restore into a fresh private state directory, verify snapshot integrity, identity and supported version, then persist a recovery hold before publishing the restored state. The hold blocks intake and external execution through every runtime entry point until a local operator records reconciliation.

Restore validates the database's schema objects against the supported version before executing migrations or writes; integrity and a checksum alone cannot detect a trigger that alters recovery records. Verify the persisted hold after writing it. A present but empty or malformed hold fails closed. Durable publication reservations block startup even if restoration crashes before creating the target database. Restoring an already-held snapshot preserves its earliest unresolved recovery boundary. Checksums do not authenticate backups; operators must preserve trusted provenance and private access.

Recovery has two explicit paths. A continuity path reconstructs missing message identities and effect fences from authoritative evidence across the whole snapshot-to-recovery interval. An operator may instead accept a history gap: record the actor, reason, snapshot identity and skipped history, then establish a fresh Graph baseline explicitly. Neither path implicitly clears the old cursor, deletes snapshot-era work or declares unknown effects safe. Queued, approved and pending delivery work requires per-run reconciliation; unknown outcomes stay fenced. Generic recovery never fabricates tool results or bypasses domain approval. Adapter-specific evidence and resolution remain necessary for uncertain business effects.

**Target operator workflow:** inspect stopped held state through bounded metadata pages, including exact record fingerprints and a binding to mailbox identity, hold and checkpoint. Preview and apply small, strictly validated recovery plans with local actor/reason and hashed evidence references. A stale fingerprint, mismatched binding or unsupported resolution fails closed. Apply each bounded batch atomically and idempotently while the hold remains. Resuming a run requires evidence of no effect, preserved cumulative budgets and normal policy/approval checks; unresolved actions stay fenced and completed tool results are never invented. Release requires reconciliation of executable snapshot-era work plus an explicit whole-window continuity attestation or history-gap acceptance. Commit the final checkpoint decision, audit and hold removal atomically; a failed or interrupted release leaves execution held. Evidence references record an operator's conclusion, not an automatic proof of the external outcome.

Legacy records with unknown budgets or malformed reservations can receive conservative terminal decisions; keep their unknown counters unchanged across restart. They cannot resume through invented budget. Abandonment requires evidence of no effects and must not conceal unresolved sends or actions. Prior action absence decisions must match their durable batch receipt and exact current action record. Completed and ignored history remains immutable. A queued snapshot with zero counters still needs external absence evidence because the old deployment may have acted after the snapshot.

**Target release review:** a strict local manifest binds the current mailbox, configuration, snapshot and recovery binding, names continuity or explicit history-gap acceptance, and attests coverage of all Graph/adapter sources from snapshot creation through a stated recovery time after the old deployment stopped. Preview stages a private decision under exclusive ownership and returns a digest covering attribution, evidence, executable ledger and old/new checkpoints. History-gap preview performs bounded read-only Graph baseline pagination; apply performs no network calls. Continuity requires an already completed original checkpoint. Each executable run must match its applied reconciliation receipt and current fingerprint; inspect only indexed active work under total row/page/time limits. Existing terminal uncertainty stays fenced. Changed state, expired work, absent proof or an unfinished baseline invalidates release. Commit the reviewed checkpoint, audit, receipt and hold removal together. An exact retry may acknowledge the prior release only while its resulting checkpoint still matches and no newer hold exists.

The old deployment's actual stop may precede snapshot creation, as in a stopped backup that is never restarted. Preserve that truthful timestamp; coverage still starts at the snapshot and ends after both restore and the old stop. A history-gap review additionally names the skipped interval through fresh-baseline observation.

Credential rotation is performed through the configured secret manager/environment. **Target:** document a staged rotation procedure that verifies replacement credentials with a read-only probe, switches the deployment, confirms readiness, then revokes the old credential. Rotation must not reset mailbox state or weaken resource scope. If both credentials cannot overlap, document the expected outage and recovery sequence.

Configuration and instruction changes are validated before they can authorize further actions. Invalid candidates fail closed and leave the last valid configuration available for diagnosis. Changes to mailbox identity, connection topology, state location, budgets, or retention require restart. Every deployment change must state whether pending work is compatible and how to roll back.

**Target:** version persistent schemas and provide explicit, restart-safe migrations with backups and a defined rollback boundary. A migration either completes atomically or leaves the prior state usable. If downgrade is unsafe after migration, block rollback to the older binary and give a forward-recovery procedure. Preserve pending approvals and fences across supported upgrades; never silently discard or reinterpret them.

**Target:** publish versioned container/package artifacts with provenance, pinned dependencies, supported Node/Linux versions, release notes, security update policy, and a maintenance/support window. Document upgrade order, compatibility, rollback limits, and recovery for each release. Do not imply an artifact is supported after its maintenance window ends.

## Release artifact promotion

The default runtime image contains the exact reviewed Node binary, production application dependencies, required native libraries and trust data. Build tools, package managers, shells and unrelated distribution utilities stay in the build stage. Pin both stages by digest and retain vendor signature, package inventory and bundled Node component provenance. Runtime minimization does not establish that retained native code is unaffected by advisories.

Compose initializes its dedicated state volume through Node filesystem APIs in the same image, with only the existing ownership capabilities and no network. Require a real directory, UID/GID 1000 and mode 0700 before the agent starts. The image itself must declare the empty state directory with those permissions; verify they survive Docker volume population and subsequent mounts. Operational controls continue through the Node CLI. Additional stdio executables require a complete reviewed bundle or derived build, including their native dependencies and advisory review; runtime installation remains unsupported. Every changed runtime image needs actual state initialization, CLI lifecycle, recovery, records stdio, TLS and exact-image scan qualification before release.

Qualify a versioned candidate once, then promote its original package, saved image and metadata bytes. Keep the candidate workflow read-only. A source-checkout-only, network-free verifier checks the bounded six-file inventory against independently reviewed version, source, platform, image and hash anchors and returns a manifest digest with `prepared-not-approved` status. It does not establish GitHub provenance, current release gates, approval or the saved image's actual payload. No publishing daemon or write-capable workflow is required.

The operator separately binds the repository identity, reviewed candidate workflow, successful run and attempt, immutable artifact ID and archive digest, and full source commit. Resolve the version tag through any annotated tag objects to that same commit. Bind actual package and saved-image layout/content qualification to their exact archive hashes; metadata inventories alone are insufficient. Require bounded entry paths/types/count/size/modes without traversal, links or unexpected payloads, exact package inventory/content and installed consumer checks with lifecycle scripts disabled, and saved-image content/source binding plus loaded image identity. Reuse unchanged qualification evidence only when archive hashes match. Review advisory dispositions, supported platforms, release notes and maintenance policy. Verify the currently public repository and the selected private reporting/support routes and their monitoring. Public repository visibility, public GHCR visibility and release publication require explicit user approval; missing gates keep promotion blocked. Changes to the candidate require new qualification rather than modifying the reviewed artifact.

Load the original image archive once and inspect its image ID, platform and source/version labels before tagging its exact version for GHCR. Before the first push, inspect the current registry version read-only: an absent version may proceed; an exact already-owned match is acknowledged without pushing again; conflicting or unknown state stops promotion without overwriting it. Do not rebuild, repack, save a replacement image archive or update `latest`. The registry manifest digest is distinct from the Docker image ID: verify the manifest's config digest and an anonymous digest pull against the qualified image ID/platform. Upload all six original files to an operator-owned GitHub draft without overwriting assets, then verify each remote size and digest. Immediately before publication, recheck tag/source binding, current gates, the registry version's recorded digest and the draft notes' approved hash over exact UTF-8 bytes with original newlines preserved. A different platform needs its own qualified candidate.

Keep a content-free promotion receipt with the approved manifest digest, actor/time, repository/workflow/run/artifact identities, source/tag, release-note hash, gate evidence references, registry digest, release/asset IDs and verified file hashes. Publication across GitHub and GHCR is not atomic. A lost response requires read-only reconciliation before another mutation; resume only exact matching owned state. Conflicting hashes, an unknown draft owner, incomplete assets, changed tags or revoked gates stop promotion for review. Never automatically delete, overwrite, retag or rebuild to hide a partial publication.

Webhooks, explicit backfill, public health endpoints, and operator notifications remain optional future capabilities. Each must define its authentication, replay protection, authorization, rate limits, failure handling, operational dependencies, and acceptance evidence before deployment is enabled.

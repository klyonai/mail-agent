# Collective design review

2026-10-01 · Design decisions applied; runtime implementation has not started.

Historical review: its multi-agent topology and two-inbox milestone were superseded by the subsequent single-stack decision below. Current target files reflect that later decision.

Three parallel subagents used simulated engineering perspectives inspired by Andrej Karpathy, Peter Steinberger, and Boris Cherny. These are synthesized review lenses, not statements or endorsements from those people. A second round examined the merged recommendations against simple setup, configurable email/model/MCP connections, broad use cases, and several agents in one daemon.

| Lens | Principal recommendations |
| --- | --- |
| Karpathy-inspired | Make the loop and context budget inspectable; start with a small complete journey; evaluate recipe behavior separately from runtime correctness |
| Steinberger-inspired | Make ordinary MCP servers work through configuration; define onboarding and recovery; avoid premature pooling/framework abstractions |
| Cherny-inspired | Give runs/actions/approvals clear contracts; enforce authority outside the model; distinguish offline preview, live probes, and real execution |

The collective retained one daemon per operator trust boundary, agent-scoped state, operator-owned instructions, bounded history, optional business memory through MCP, and CLI administration. It agreed on the following changes to the target:

- **A coherent first slice:** two text inboxes using direct replies and one model dialect. No MCP, multimodal capability, or tool calling is required. Image transcription and configured MCP are committed next capabilities; PDF input follows demonstrated image processing.
- **A bounded execution contract:** one request creates one run. Replies and tool proposals are validated; the runtime controls effects. Define waiting/completion/failure/uncertainty states, deterministic context selection, and cumulative budgets across resumes. Exhaustion cannot trigger an extra unbudgeted model call.
- **Two MCP authorization patterns:** ordinary servers use dedicated credentials and an explicitly shared sender/resource scope. Domain adapters enforce differing per-user visibility and revision-sensitive writes. A generic connection never implies these domain guarantees.
- **Current authority wins:** both automatic and approved actions use the same executor. Recheck permissions before reads, mutations, and prepared sends. Revocation can suspend approvals despite historical instruction snapshots.
- **Predictable lifecycle:** daemon errors and identity collisions prevent startup; invalid individual bundles disable those agents. Candidate reload is atomic. Offline fixture preview and explicit live probes have different guarantees.
- **Useful evidence:** safe diagnostic metadata and synthetic acceptance cases explain failures. Model quality requires actual recipe evaluation; fixture preview proves no live model quality.

Final consistency review caught an approval deadlock: approval replies cannot wait behind the conversation run they must resume. The architecture now routes verified approvals as deduplicated control inputs and rechecks both actors before continuation. Generic MCP acceptance also explicitly distinguishes shared scope from domain visibility.

The review resolved a sequencing disagreement in favor of a text-first milestone: it proves mailbox lifecycle and multi-agent isolation with fewer dependencies. The document inbox remains a defining product journey. Shared MCP sessions, credential-cache frameworks, dynamic instruction discovery, summaries, UI, and distributed workers remain deferred until a deployment justifies them.

Next implementation step: build configuration validation, two isolated runtimes, fixture-backed mail/model adapters, and the durable run/outbox path. Complete the ten acceptance cases in [features](../features.md), then qualify real Graph/model connectors through an opt-in synthetic tenant journey. Add image/file delivery and MCP on that same loop. The revised design establishes the implementation sequence; it makes no claim of deployed behavior.

## Subsequent decision: one email stack

The user chose one mailbox agent per process/container to simplify ownership and avoid shared runtime infrastructure. Each deployment owns its configuration, credentials, MCP sessions/local servers, database, and artifacts. Additional inboxes use additional deployments. External business resources are shared only by deliberate configuration; a common MCP endpoint does not imply separate backing state.

The first milestone is now one text inbox with durable runs/outbox and the same safety/recovery acceptance cases. Multi-agent supervision and pooling are deferred. The review's execution-loop, authorization, context-budget, and approval-deadlock recommendations remain part of the target design.
